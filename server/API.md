# PotsHaven API

Node 24 built-in SQLite stores data under `.data/potshaven.db`. First run creates clearly labelled demo data; subsequent starts never reseed or overwrite changes. All dates are ISO date strings. The interface calls saved locations **Sites**; the existing `places` collection and job `placeId` references remain unchanged, so this navigation change does not migrate or duplicate company records.

For a new company database with no sample records, set `DATA_SEED=false` on its first start. This never clears an existing database. `DATA_DIR` can select a separate persistent directory, allowing the demo database to remain intact. A database first created without sample data stays free of demo records on subsequent starts even if the flag is later omitted.

- `GET /api/health` is public and performs a real database read on every request, including warm Vercel instances. PostgreSQL checks the settings, records and media tables without returning company records or image contents. Success returns `ok`, `database: "connected"`, `demoMode`, `authenticated`, `role`, `imageGenerationConfigured`, `assistantConfigured`, `imageModel`, `imageQuality`, `imageSize`. A failed connection returns HTTP 503 and a fixed, secret-free database diagnostic. Application startup alone does not establish database readiness. Read-only database calls retry one transient connection failure; mutations never automatically repeat.
- `POST /api/auth/login {role: 'owner'|'manager', password}` sets a signed HttpOnly SameSite cookie for 12 hours. `POST /api/auth/logout` clears it. With neither password configured, local demo mode grants owner access. Session signatures are bound to the current password configuration using a keyed derivation from the retained server secret: enabling or changing either password invalidates all previously issued sessions, including demo sessions.
- `GET /api/state` returns role-filtered collection arrays, `settings`, current `role`, `demoMode`, `imageGenerationConfigured` and `assistantConfigured`. Image model/quality/size details are owner-only.
- Money features are disabled by `FINANCIAL_FEATURES_ENABLED=false` in `src/features.js` for both roles. `payments` and `expenses` are empty in state and direct endpoints return 403. Structured money fields (including costs, budgets, amounts, pay rates and currency) are recursively omitted from returned records/settings and rejected in writes. Receipt-type supply records are hidden and cannot be mutated. Existing values remain in storage, including internal stock costs; ordinary operational edits preserve hidden fields. Contracts remain owner-only API records with amounts omitted, but have no current UI or assistant workflow.
- Collections: `places`, `jobs`, `inventory`, `stockMovements`, `workers`, `vehicles`, `contracts`, `payments`, `expenses`, `purchaseRequests`, `equipment`, `issues`, `careGuides`, `designs`.
- `GET /api/:collection`, `POST /api/:collection`, `PATCH /api/:collection/:id`, `DELETE /api/:collection/:id` are supported. POST assigns an ID and returns the record. PATCH returns the updated record. DELETE returns 204. Linked records must be unlinked first. Stock movements are immutable.
- Collection PATCH requests may include an optional `_expected` object containing the role-filtered record the client originally opened. The server compares this baseline with the current permitted record and returns 409 if it changed; `_expected` is not stored. The database then checks the full current record under its write lock before saving. Forms using this precondition retain the draft and ask the user to refresh after a conflict. Older API clients may omit the client baseline; they still use the applicable server transaction checks but do not get a comparison against their form-opening snapshot.
- Workers optionally accept `workforceType` (`Internal`, `External`), `engagementType` (`Permanent`, `Daily`, `Weekly`, `Fixed contract`, `Until job complete`), `engagementStart`, `engagementEnd`, `relatedJobId`, `agreementStatus`, `agreementReference`, and `agreementNotes`. Temporary agreements require a start date; fixed contracts require an end date; completion agreements require a linked job. Existing worker records without these fields remain valid. Pay fields are unavailable while money features are disabled; existing values are preserved.
- `PATCH /api/places/:id {inspection:{id,date,plantHealth?,irrigation?,workNeeded?,notes?,photos?,image?}}` appends one site visit for either role and returns the updated, role-filtered site. Submit this separately from other site edits. Use a stable unique `id` (1–200 letters, digits, `_` or `-`), an actual ISO date, and at most four photos. Photos follow the existing authenticated media rules. Existing visits/private metadata are retained. Repeating the same entry ID/content returns the saved site without duplicating the visit or owner event; reusing that ID for different content returns 409. Concurrent appends retry only confirmed, uncommitted snapshot conflicts, for up to three attempts; connection failures are not replayed. Whole `inspections` list updates that omit saved visits are rejected with 409 to prevent stale forms from erasing history.
- Generated design conversations store optional `studioTitle`, `favorite`, and `approvedDesignId` on their first version. `placeId` links the conversation to a saved site. These are metadata updates through the ordinary authenticated designs API; choosing a version does not replace other image versions or publish it.
- Maintenance jobs accept `recurrence`: `None`, `Weekly`, `Fortnightly`, `Monthly`, `Quarterly`. When PATCH transitions a recurring maintenance job to `Completed`, the same database transaction creates one `Scheduled` follow-up with the next future occurrence, reset task checkboxes/photos, preserved crew/vehicle, and a shifted deadline. The completed record receives `nextJobId`; its follow-up receives `previousJobId`. Repeating completion or reopening/completing the same visit does not create duplicate follow-ups.
- `POST /api/inventory/:id/use {quantity, jobId?, note?}` atomically deducts inventory, rejects negative balances, and returns `{item,movement}`. `POST /api/inventory/:id/restock {quantity,note?}` adds stock. Direct inventory quantity edits also write a stock adjustment movement. Stored movements retain internal `unitCost` and `totalCost`, but API responses omit these while money features are disabled.
- `PATCH /api/settings` merges `companyName`, `ownerName`, `tagline`, `email`, `phone`, `logo`, `watermark`, `address`, `accentColor`; owner access required. Accent colours must use six-digit hex format. Currency updates are currently rejected with the other financial fields. Logos accept PNG, JPEG or WebP data URLs or HTTPS URLs.
- Owner/manager access is enforced through server-side collection and field allowlists. Managers receive operational sites/jobs/stock/workers/vehicles/equipment/issues/care guides and their role’s supply requests. Designs and contracts are empty arrays in manager state; direct reads return 403. Payments and expenses are unavailable to both roles. Worker pay/private terms, stock costs, job budgets, private metadata, and owner settings are omitted. All CRUD and stock responses follow the same filtering. See [role boundaries](../docs/ROLE_WORKSPACES.md).
- Manager writes cover Maintenance visits, operational progress/crew/vehicles/checklists/photos, site notes/issues, worker availability, vehicle status/notes, and pending supply/service requests. Project creation/contractual deadlines, hiring, fleet creation, branding changes, stock editing/restocking, approvals and all deletes are owner-only. Financial changes are unavailable to both roles. Stock usage remains job-linked and its response omits costs; stored costs are retained but not returned to either role while disabled. Manager-created references must identify existing approved sites, workers and vehicles.
- `GET /api/activity?limit=100` is owner-only and returns `{items, unreadCount}`. The default limit is 50; accepted limits are integers from 1 to 100. Items are newest first, while `unreadCount` covers all stored unread events, not just the returned page. Each event contains `id`, `actor: "Manager account"`, `action`, `collection`, `recordId`, `title`, `summary`, `createdAt`, `readAt`, site metadata when available, and optional `jobId` or stock `quantity`/`unit`.
- `POST /api/activity/:id/read` returns `{item}` with durable `readAt`; `POST /api/activity/read-all` marks all current events read and returns `{ok:true}`. Both require the owner. Managers cannot list or acknowledge events, and clients cannot create arbitrary activity records. Authentication and same-origin write protections apply.
- Permitted manager creates/updates, job completion/assignments, site visits, requests and stock use generate limited operational activity. The record mutation and event commit in one SQLite/PostgreSQL transaction; rejected writes or failed event insertion leave neither change committed. Owner changes and unchanged manager updates do not create manager events. Events are not backfilled for pre-existing records. The owner browser requests the latest 100, checks every 30 seconds while visible and on focus/reconnection, and supports manual refresh. This is an in-app inbox, not email, push or WhatsApp delivery. Shared-role attribution identifies the manager account, not an individual worker.
- Media requires authentication and a permitted record reference for manager access. Private design media and attempts to attach its URL to an operational record are rejected. Media responses use `Cache-Control: private, no-store` and `Vary: Cookie`.
- `GET /api/assistant/briefing?today=YYYY-MM-DD` returns a grounded `{summary,total,items:[{id,title,detail,page,kind}]}` daily briefing from saved records: overdue work, completed jobs with unchecked tasks, missing crew/transport, worker availability, low stock, issue follow-ups, and expiring worker engagements. Contract-renewal and financial alerts are disabled. It needs a signed-in owner/manager but no OpenAI key. `today` defaults to the server's current UTC date; the browser supplies its local date.
- `POST /api/assistant {message,history?:[{role:'user'|'assistant',content}],today?}` answers company questions and prepares up to five proposed changes. The response is `{reply,actions:[{id,label,collection,operation,recordId?,changes,warnings?}]}`. Owner proposals support creating/updating jobs, workers, vehicles and issues with server-validated fields, enums and existing reference IDs. Manager proposals follow the same operational write limits as ordinary requests; hiring, fleet creation, private pay/terms and contractual project changes are rejected. Assistant snapshots and briefings use role-filtered data and exclude financial fields for both roles; proposed financial changes are rejected. This route never writes records. The manager reviews each proposal before the browser applies it through the ordinary collection APIs; proposals are not automatically retried. The browser checks the latest saved record before applying an update and blocks it if the record changed since the request was prepared. Warnings highlight unavailable workers/vehicles and other assignments on the same day without claiming time overlaps when visit durations are unknown.
- The company assistant shares the server-only `POTSHAVEN_OPENAI_KEY` / `OPENAI_API_KEY`, uses the OpenAI Responses API with strict structured output, and defaults to `gpt-5.4`. Optional `POTSHAVEN_ASSISTANT_MODEL` overrides the text model independently of image generation. Requests use a bounded snapshot (at most 80 records per collection, trimmed to 100,000 characters by removing whole records); image contents, dedicated contact fields, credentials and company settings are omitted. Editable checklists/skills are sent in full; oversized or legacy lists are marked read-only and cannot be replaced by a proposal. Updating a record omitted from the current snapshot is rejected. Conversation context is limited to ten messages, 4,000 characters per message and 16,000 characters combined; the current message accepts 1–4,000 characters. Model output is revalidated server-side. Calls have a 60-second timeout, per-instance concurrency/rate limits, proxy support and no automatic paid retry; Responses API requests set `store:false`. Configured-key booleans confirm configuration, not billing or model access.
- `POST /api/designs/generate {prompt, referenceImages?:dataURL[], parentDesignId?, placeId?}` creates an image or edits a saved version. Prompts accept 1–6,000 characters. Attach up to four PNG/JPEG/WebP photos per message; combined data URLs must fit within 3.2 MiB. The browser automatically prepares photos within 1,600px/600 KiB each. `parentDesignId` uses the actual saved image as the primary edit reference and carries the original brief, recent instructions and site-photo context. Each response is a new design record with `conversationId`, `parentDesignId`, current-message `referenceImages` media URLs, inherited `contextImages`, bounded `instructionHistory`, and `source: "Design studio"`. Earlier versions remain unchanged, including when branching from an older version. Legacy `originalImage` and `measurements` fields are still accepted; the chat has no separate measurements field.
- Image generation requires server-only `POTSHAVEN_OPENAI_KEY` or `OPENAI_API_KEY`. Defaults remain `gpt-image-2.5-sunburst`, quality `max`, size `2560x1440`, JPEG95 output. Optional `POTSHAVEN_IMAGE_MODEL`, `POTSHAVEN_IMAGE_QUALITY`, `POTSHAVEN_IMAGE_SIZE` (or corresponding `OPENAI_` variables) override these settings. Older model overrides default to compatible `high` quality and `1536x1024` size. Model availability depends on the connected account; a missing key returns explicit 503. Generated images and uploaded references use authenticated media routes, with durable Supabase storage on Vercel. Requests retain inherited proxy settings and TLS verification, with a four-minute generation timeout within Vercel's five-minute function limit. The API domain `api.openai.com` must be allowed by the environment. Paid generation requests are never automatically retried.

Errors return `{error: string}` with an appropriate HTTP status. No secret values are returned. Configure `APP_OWNER_PASSWORD` and `APP_MANAGER_PASSWORD` for private shared operation. Live email/SMS/WhatsApp delivery is not part of this server: the frontend generates shareable WhatsApp messages for a manager to send.

`npm start` serves the compiled application and remains usable as a local demo without passwords. Production serving does not by itself enable authentication: configure both role passwords before exposing company data to other users. `GET /api/health` and the UI explicitly report demo mode when neither password exists. Vite preserves the browser's host through its API proxy so same-origin write checks work without an extra origin allowlist.

Image model and parameter defaults follow the current official OpenAI Python SDK definitions, checked during implementation:

- [Image models](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_model.py)
- [Generation parameters](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_generate_params.py)
- [Edit parameters](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_edit_params.py)

Image transport tests inject a fake `fetchImage` response, verifying generation, multi-photo edits, conversation context, saved versions, durable media and legacy-model compatibility without making paid external API requests.
