# PotsHaven API

Node 24 built-in SQLite stores data under `.data/potshaven.db`. First run creates clearly labelled demo data; subsequent starts never reseed or overwrite changes. All dates are ISO date strings. Currency defaults to GHS.

For a new company database with no sample records, set `DATA_SEED=false` on its first start. This never clears an existing database. `DATA_DIR` can select a separate persistent directory, allowing the demo database to remain intact. A database first created without sample data stays free of demo records on subsequent starts even if the flag is later omitted.

- `GET /api/health` is public and performs a real database read on every request, including warm Vercel instances. PostgreSQL checks the settings, records and media tables without returning company records or image contents. Success returns `ok`, `database: "connected"`, `demoMode`, `authenticated`, `role`, `imageGenerationConfigured`, `assistantConfigured`, `imageModel`, `imageQuality`, `imageSize`. A failed connection returns HTTP 503 and a fixed, secret-free database diagnostic. Application startup alone does not establish database readiness.
- `POST /api/auth/login {role: 'owner'|'manager', password}` sets a signed HttpOnly SameSite cookie for 12 hours. `POST /api/auth/logout` clears it. With neither password configured, local demo mode grants owner access. Session signatures are bound to the current password configuration using a keyed derivation from the retained server secret: enabling or changing either password invalidates all previously issued sessions, including demo sessions.
- `GET /api/state` returns every collection array, the `settings` object, current `role`, `demoMode`, `imageGenerationConfigured`, `assistantConfigured`, `imageModel`, `imageQuality`, and `imageSize`.
- Collections: `places`, `jobs`, `inventory`, `stockMovements`, `workers`, `vehicles`, `contracts`, `payments`, `expenses`, `purchaseRequests`, `equipment`, `issues`, `careGuides`, `designs`.
- `GET /api/:collection`, `POST /api/:collection`, `PATCH /api/:collection/:id`, `DELETE /api/:collection/:id` are supported. POST assigns an ID and returns the record. PATCH returns the updated record. DELETE returns 204. Linked records must be unlinked first. Stock movements are immutable.
- Workers optionally accept `workforceType` (`Internal`, `External`), `engagementType` (`Permanent`, `Daily`, `Weekly`, `Fixed contract`, `Until job complete`), `engagementStart`, `engagementEnd`, `relatedJobId`, `agreedRate`, `rateBasis` (`Daily`, `Weekly`, `Fixed`), `agreementStatus`, `agreementReference`, and `agreementNotes`. Temporary agreements require a start date; fixed contracts require an end date; completion agreements require a linked job. Existing worker records without these fields remain valid. Pay terms do not create financial transactions.
- Generated design conversations store optional `studioTitle`, `favorite`, and `approvedDesignId` on their first version. `placeId` links the conversation to a saved place. These are metadata updates through the ordinary authenticated designs API; choosing a version does not replace other image versions or publish it.
- Maintenance jobs accept `recurrence`: `None`, `Weekly`, `Fortnightly`, `Monthly`, `Quarterly`. When PATCH transitions a recurring maintenance job to `Completed`, the same SQLite transaction creates one `Scheduled` follow-up with the next future occurrence, reset task checkboxes/photos, preserved crew/vehicle, and a shifted deadline. The completed record receives `nextJobId`; its follow-up receives `previousJobId`. Repeating completion or reopening/completing the same visit does not create duplicate follow-ups.
- `POST /api/inventory/:id/use {quantity, jobId?, note?}` atomically deducts inventory, rejects negative balances, and returns `{item,movement}`. `POST /api/inventory/:id/restock {quantity,note?}` adds stock. Direct inventory quantity edits also write a stock adjustment movement. Usage movements carry `unitCost` and `totalCost` for project costing.
- `PATCH /api/settings` merges `companyName`, `ownerName`, `tagline`, `email`, `phone`, `currency`, `logo`, `watermark`, `address`, `accentColor`; owner access required. Currency must be a supported uppercase ISO code; accent colours must use six-digit hex format. Logos accept PNG, JPEG or WebP data URLs or HTTPS URLs.
- Manager access covers normal operations and purchase requests. Only owners approve/reject purchases or update reviewed requests.
- `GET /api/assistant/briefing?today=YYYY-MM-DD` returns a grounded `{summary,total,items:[{id,title,detail,page,kind}]}` daily briefing from saved records: overdue work, completed jobs with unchecked tasks, missing crew/transport, worker availability, low stock, issue follow-ups, and expiring engagements/contracts. It needs a signed-in owner/manager but no OpenAI key. `today` defaults to the server's current UTC date; the browser supplies its local date.
- `POST /api/assistant {message,history?:[{role:'user'|'assistant',content}],today?}` answers company questions and prepares up to five proposed changes. The response is `{reply,actions:[{id,label,collection,operation,recordId?,changes,warnings?}]}`. Proposals support creating/updating jobs, workers, vehicles and issues with server-validated fields, enums and existing reference IDs. This route never writes records. The manager reviews each proposal before the browser applies it through the ordinary collection APIs; proposals are not automatically retried. The browser checks the latest saved record before applying an update and blocks it if the record changed since the request was prepared. Warnings highlight unavailable workers/vehicles and other assignments on the same day without claiming time overlaps when visit durations are unknown.
- The company assistant shares the server-only `POTSHAVEN_OPENAI_KEY` / `OPENAI_API_KEY`, uses the OpenAI Responses API with strict structured output, and defaults to `gpt-5.4`. Optional `POTSHAVEN_ASSISTANT_MODEL` overrides the text model independently of image generation. Requests use a bounded snapshot (at most 80 records per collection, trimmed to 100,000 characters by removing whole records); image contents, dedicated contact fields, credentials and company settings are omitted. Editable checklists/skills are sent in full; oversized or legacy lists are marked read-only and cannot be replaced by a proposal. Updating a record omitted from the current snapshot is rejected. Conversation context is limited to ten messages, 4,000 characters per message and 16,000 characters combined; the current message accepts 1–4,000 characters. Model output is revalidated server-side. Calls have a 60-second timeout, per-instance concurrency/rate limits, proxy support and no automatic paid retry; Responses API requests set `store:false`. Configured-key booleans confirm configuration, not billing or model access.
- `POST /api/designs/generate {prompt, referenceImages?:dataURL[], parentDesignId?, placeId?}` creates an image or edits a saved version. Prompts accept 1–6,000 characters. Attach up to four PNG/JPEG/WebP photos per message; combined data URLs must fit within 3.2 MiB. The browser automatically prepares photos within 1,600px/600 KiB each. `parentDesignId` uses the actual saved image as the primary edit reference and carries the original brief, recent instructions and site-photo context. Each response is a new design record with `conversationId`, `parentDesignId`, current-message `referenceImages` media URLs, inherited `contextImages`, bounded `instructionHistory`, and `source: "Design studio"`. Earlier versions remain unchanged, including when branching from an older version. Legacy `originalImage` and `measurements` fields are still accepted; the chat has no separate measurements field.
- Image generation requires server-only `POTSHAVEN_OPENAI_KEY` or `OPENAI_API_KEY`. Defaults remain `gpt-image-2.5-sunburst`, quality `max`, size `2560x1440`, JPEG95 output. Optional `POTSHAVEN_IMAGE_MODEL`, `POTSHAVEN_IMAGE_QUALITY`, `POTSHAVEN_IMAGE_SIZE` (or corresponding `OPENAI_` variables) override these settings. Older model overrides default to compatible `high` quality and `1536x1024` size. Model availability depends on the connected account; a missing key returns explicit 503. Generated images and uploaded references use authenticated media routes, with durable Supabase storage on Vercel. Requests retain inherited proxy settings and TLS verification, with a four-minute generation timeout within Vercel's five-minute function limit. The API domain `api.openai.com` must be allowed by the environment. Paid generation requests are never automatically retried.

Errors return `{error: string}` with an appropriate HTTP status. No secret values are returned. Configure `APP_OWNER_PASSWORD` and `APP_MANAGER_PASSWORD` for private shared operation. Live email/SMS/WhatsApp delivery is not part of this server: the frontend generates shareable WhatsApp messages for a manager to send.

`npm start` serves the compiled application and remains usable as a local demo without passwords. Production serving does not by itself enable authentication: configure both role passwords before exposing company data to other users. `GET /api/health` and the UI explicitly report demo mode when neither password exists. Vite preserves the browser's host through its API proxy so same-origin write checks work without an extra origin allowlist.

Image model and parameter defaults follow the current official OpenAI Python SDK definitions, checked during implementation:

- [Image models](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_model.py)
- [Generation parameters](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_generate_params.py)
- [Edit parameters](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/image_edit_params.py)

Image transport tests inject a fake `fetchImage` response, verifying generation, multi-photo edits, conversation context, saved versions, durable media and legacy-model compatibility without making paid external API requests.
